# Delivery Gate, Phase 4: the user interface and first usable product

Status: built, tested, stopped for review. Fixture-driven: no live PayPal, no authentication, no production database, no deployment.
Run it: `python3 -m delivery_ui --port 8080` then open http://127.0.0.1:8080 (stdlib only, no installs). Tests: `python3 -m unittest discover -s tests -t .` (400 tests).
Screenshots: `docs/screens/` (captured from the running app with Playwright + Chromium; the capture script was not kept in this repository, so these images are static records).

## 1. What has been implemented
A server-rendered web app (Python stdlib `http.server`, plain HTML/CSS, a small progressive-enhancement script; no framework, no new dependency).
- **Overview**, **Payments**, **Evidence** (the only navigation, as briefed).
- **Payments**: KPI counters, filter chips, search, table (transaction, order, amount, payment status, dispute, assessment), selectable summary panel.
- **Transaction detail** (centre of the product): header card, assessment banner, *Payment information* (what PayPal reports) beside *Your information* (what the merchant provided), Assessment summary, Next steps, and four tabs: **Evidence**, **Assessment details**, **What changes?**, **Provenance**.
- **Evidence workspace**: paste text, choose a text file (click, keyboard or drag/drop), a sample library, analysis status, extracted facts table, evidence list.
- **Evidence page** per artifact: original text with exact-span highlighting, extracted facts (ambiguity, attribution, how stated, extraction confidence), source authenticity card, reviewer controls.
- Eight consistent fixture payments (the six scenarios plus an external-route case, a not-as-described case, and a no-dispute payment).

## 2. What a user can actually do (each step tested in a real browser)
Browse and search payments; open a payment and see PayPal's reported facts kept apart from their own; add evidence by paste or text-file upload (or a built-in sample); watch the existing extraction read it; inspect each fact against the original text; record a review as a named reviewer (attest a carrier document, record it as their own statement, reject a fact, undo); update the answers they provide (location, transaction-details address, redirect, PayPal responses); see the deterministic result in plain language; expand every requirement (meaning, support, what is missing, policy source); ask "what changes?" and compare; then do it for real and see the same result; inspect provenance and an activity log.

## 5. Architecture and data flow
```
browser ──HTTP──> server.py (routes, strict JSON field whitelists, CSP, no business logic)
                    │
                    ├─> render.py (HTML from view-models)  <── presenter.py (maps engine values to plain language; decides nothing)
                    │                                              ▲
                    └─> service.py (application service; in-memory demo state)
                          ├─ PayPal fixture ──> paypal_adapter.observe_order / observe_dispute / to_case / build_exposure    (Phase 3)
                          ├─ evidence text ───> extractor ──> run_extraction ──> CandidateFacts + contradictions            (Phase 2)
                          ├─ reviewer action ─> ReviewDecision / Attestation ──> bridge.build_case  (the authority on what a reviewer may do)
                          └─ Case ────────────> engine.assess / engine.counterfactual                                       (Phase 1)
```
- The UI never computes a protection result. `assess()` is the only source, and a test rebuilds every payment from the Phase 1-3 public APIs *without the service* and requires an identical assessment digest.
- A refused reviewer action (for example attesting a merchant statement as a carrier document) is refused by the existing bridge, not by UI logic.
- The what-if builds hypothetical evidence through the same bridge and hands it to `engine.counterfactual`. Tested: the hypothetical digest equals the digest after really adding and reviewing the evidence.
- Server-only secrets: the extraction key is read from the server environment; a test proves it never reaches a page, the API or the JS.
- Fixture data is labelled everywhere ("Fixture data" badge on every page; every observation has `origin=FIXTURE`).

## 7. Tests
**400 tests, all passing** (248 baseline, untouched + 152 new). New: 40 service, 35 presenter, 52 HTTP/screens, 21 real-browser (Chromium; skipped automatically where Playwright is absent), 4 mutation-battery tests.
Covered: transaction display; evidence submission; extraction integration (recorded, injected model output, validation failure, extractor failure, unavailable); assessment rendering; unknown values; contradictions; provenance and exact spans; authenticity distinctions; counterfactual faithfulness; forbidden protection claims on every screen; loading, empty and error states; consistency across screens; escaping/XSS; secrets; API strictness; responsive overflow at five widths; no console or CSP errors.
**12 UI mutants, all caught** by the property they violate (UI computes its own result, unknown shown as demonstrated, merchant statement shown as demonstrated, notice dropped, API accepts a supplied result, bridge safeguards bypassed, highlighting alters text, what-if drops evidence, secret leaked, "Verified" label, potential exposure shown as known, unknown route shown as known). Cumulative mutation checks across phases: 47.
Defects found and fixed during the build (not hidden): the Payments page initially lacked the page shell; the payments table and KPI grid overflowed at phone width; the double-submit guard was claimed but not enforced; my first "forbidden claim" guard flagged our own disclaimer; internal engine text ("DO NOT MODEL", `physical_goods is True`) leaked into the primary view; unknown results had no on-page explanation; one browser test was flaky because Playwright's headless file-chooser interception is intermittent (the test now asserts the app's own behaviour).

## 8. Remaining limitations
- **No live extraction here.** Only the 15 built-in samples can be read offline (recorded outputs). Any other text is saved as "not read" with the reason. With `EXTRACTION_MODEL` and `ANTHROPIC_API_KEY` set on the server the existing live extractor is used; that path is tested with an injected model but has **not** been exercised against a live model.
- **Files:** text only (.txt, .eml, .csv, .md), up to 200 KB. PDFs and images cannot be read; the UI says so.
- **Reviewer identity is a typed name**; there is no sign-in. A merchant can therefore attest their own document. The UI says what an attestation means and that it is not independent verification.
- **State is in memory** and resets when the server restarts ("Reset demo data" also does).
- **What-if** covers reviewing evidence already on the payment, or adding a library sample. It has no free-form "enter the details you expect" mode.
- Single merchant, no pagination, English only. Tested in Chromium only (no Firefox/Safari); basic accessibility (labels, focus, roles, keyboard dropzone) but no screen-reader audit.
- The Phase 3 questions are still open (EXTERNAL route mapping, not-as-described normalisation, capture-to-dispute linkage, SNAD exposure policy change). The UI shows them as unknown rather than guessing. The engine's SNAD "exposure_floor" is deliberately not displayed.

## 9. Differences from the approved design
Design elements that **could not be supported by the existing backend** (reported, not worked around):
| Design element | What I did instead | Why |
|---|---|---|
| Percentage rings (85%, 80%) and "Mostly Complete / Mostly Met" | Counts plus the engine's own status | The engine produces no score; a percentage would be invented analytics and implies partial protection |
| "Likely to Qualify" | "Requirements demonstrated" with a *Hypothetical* banner and "PayPal makes the final decision" | A prediction is forbidden; the engine returns a modeled assessment only |
| "Verified" badges | "Reviewed", with "not independently verified" | VERIFIED can only come from an independent source; none exists |
| "AI Analysis in Progress 70%" progress bar | Real step status (read, extracted, validated, contradiction check) shown when complete | Extraction here is synchronous; there is no progress to report |
| Import Email, Track Order, Add Tracking Link | Sample evidence library | No email or carrier integration exists |
| Upload of PDFs, images "and more" (max 25 MB) | Text files up to 200 KB, stated plainly | The extraction pipeline reads text only |
| "Customer Message … Conflict" evidence row | Customer's claim shown as PayPal's dispute reason | No customer-message source exists in PayPal fixtures |
| "Valid transaction", "Timely delivery", "Signature available" requirements; "Payment Details: Met" | Only the engine's own requirements | They are not modeled; signature confirmation is explicitly not modeled |
| Assessments, Activity navigation; Settings; Help; Export Report; notification bell; "Merchant Tools" | Not built | No working functionality; the brief limits navigation to Overview / Payments / Evidence. The activity log lives in the Provenance tab |
| Sidebar tagline "Stronger protection" | "Fixture demo. PayPal makes the final decision." | Reads as a protection claim |
| Data in the mock-ups (Lagos NG, DHL, UPS, 1Z8F…) | Consistent US fixtures | The engine models U.S. rules only |

Design decisions where the brief and the screenshots disagreed:
- **Colour:** the screenshots use a blue accent and a cool grey background; the brief's brand system specifies Deep Teal for actions, Navy for structure and Warm Ivory for the background. I used the brand system with the design's layouts.
- **Confidence column:** kept (it is in the design) but relabelled "Extraction confidence" with a note that it describes only how clearly the text was read and is never used in the assessment.
- **Red/amber:** "Requirements not demonstrated" is red in the table pill and amber in the detail banner, as in the design.

Additions not in the design (needed for working functionality): Overview page; "Your information" form; reviewer controls; sample library; policy notice bar (the engine requires its notice to be shown); explanation card for unresolved conditions; global Evidence index.
